아래 내용은 워크플로우 각 단계에 대한 세부 가이드입니다. 필요한 경우에만 해당 섹션으로 이동하여 내용을 읽습니다.

# 변경 사항 확인 가이드

풀리퀘스트가 병합될 원격 브랜치를 파악합니다.
기본적으로 `origin/develop` 브랜치를 병합 대상으로 합니다.
단, 해당 브랜치로 병합하는 것이 맞는지 사용자에게 **반드시 확인을 받습니다.** (옵션: 예 / 아니요(다른 브랜치명 입력))

확인이 끝나면 Diff 명령을 실행하여 병합 대상 브랜치와 현재 브랜치 간 변경사항을 파악합니다.
```sh
git diff {병합 대상 브랜치}...HEAD
# 예) git diff origin/develop...HEAD
```
Diff 내역뿐만 아니라 변경을 진행한 컨텍스트(대화 내용, 커밋 메시지 등)도 함께 참고합니다.

# 풀리퀘스트 제목 작성 가이드

PR 제목은 아래 템플릿을 따릅니다.
```
[PICK-{작업 번호}] 간략한 작업 소개입니다.
# 예) [PICK-112] 간략한 작업 소개입니다.
```

작업 번호는 아래 방법으로 획득합니다.

HEAD의 브랜치명을 확인합니다. 브랜치명은 다음 형식으로 설정되어 있습니다.
마지막 '/' 뒤의 'PICK-' 문자열 다음부터 작업 번호가 위치합니다.
```
feature/PICK-{작업 번호}
# 예) feature/PICK-112, feature/PICK-113
```
위 방식으로 작업 번호를 획득할 수 없는 경우 사용자에게 작업 번호 입력을 요청합니다.

# 풀리퀘스트 본문 작성 가이드

`{프로젝트 루트}/.github/pull_request_template.md` 경로에서 풀리퀘스트 템플릿을 읽고, 해당 템플릿의 구조를 따릅니다.

작업 내용은 사용자의 별도 요청이 없다면 최대한 간략하게 작성합니다.
아래 지시사항을 **반드시 준수**합니다.

1. 변경사항은 필요시 여러 도메인으로 분류합니다.
```
[변경사항1]
- 세부 내역1
- 세부 내역2

[변경사항2]
- 세부 내역1
- 세부 내역2
```
2. 어조는 "~합니다"로 통일합니다.
3. 체크리스트 섹션은 스킬 호출 시 사용자의 요청이 없다면 작성하지 않고 "생략"으로 표기합니다.
4. 전체적인 작성 사항을 한 번 더 검토합니다. 아래 리스트 요소들에 대해 자가 검진을 수행합니다.
  - 부자연스러운 설명은 없는지 확인합니다.
  - 도메인과 일치하지 않는 세부 설명은 없는지 확인합니다.
  - PR 본문의 첫 설명, 타이틀이 전체 작업 사항과 일치하는지 확인합니다.

# 풀리퀘스트 생성 및 후처리 가이드

작성한 제목과 본문으로 풀리퀘스트를 생성합니다.

1. 현재 브랜치가 원격(`origin`)에 푸시되어 있는지 확인하고, 푸시되지 않았다면 먼저 푸시합니다.
```sh
git push -u origin HEAD
```

2. `gh` CLI로 풀리퀘스트를 생성합니다. 본문은 임시 파일로 작성한 뒤 `--body-file`로 전달합니다.
```sh
gh pr create \
  --base {병합 대상 브랜치} \
  --title "[PICK-{작업 번호}] 작업 소개" \
  --body-file {본문 파일 경로} \
  --assignee @me
```
- `--base`에는 '변경 사항 확인' 단계에서 확정한 병합 대상 브랜치명을 입력합니다. (`origin/` 접두사는 제외합니다. 예: `develop`)
- Assignee로 현재 사용자(`@me`)를 지정합니다.

3. 생성이 완료되면 사용자에게 생성된 풀리퀘스트 URL을 안내합니다.
